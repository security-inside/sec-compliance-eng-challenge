SOLUTION · TECHNICAL WALKTHROUGH

Security decisions in the request path

IMPLEMENTED CONTROLS

This implementation follows the brief’s two components: a Python client on the Linux host and a small central API. The client sends JSON by default or the documented field/value CSV; the API validates both into one snapshot, persists JSON in PostgreSQL, and produces the required CSV evidence in MinIO. A separate browser UI makes the query and evidence paths visible.

EVIDENCE FLOW

One snapshot, from collection to review

FOUR STEPS
  1. 1
    Collect

    The agent builds a bounded JSON snapshot and attaches its execution ID.

  2. 2
    Authenticate & validate

    The API verifies the credential-to-server mapping and rejects oversized or invalid payloads.

  3. 3
    Persist & export

    PostgreSQL records the snapshot; MinIO receives a CSV. The record is marked available only after upload succeeds.

  4. 4
    Review & verify

    The reviewer queries recent snapshots. The API recomputes the CSV digest before download.

Failure path: if object storage is unavailable, the record remains failed/pending and an identical replay can retry the export. Changed content with the same execution ID is rejected.

04
Reviewer console

Lists configured clients, presents host summaries and evidence status, and offers a CSV only after a stored digest check.

↑Viewer token stays in page memory; process and user names are not rendered in the dashboard.
SAFE INGESTION · WHY IT MATTERS

Authenticate · validate · bind

  • Credential mapping prevents an agent token from claiming another configured server ID.
  • Streaming byte limit + strict schema bound resource use and reject unexpected data.
  • UTC timestamps + unique execution ID make records easier to compare and replay safely.
  • Bound SQL parameters + CSV formula neutralization reduce common injection risks at storage/export boundaries.
EVIDENCE LIFECYCLE · WHY IT MATTERS

Persist · retry · verify

  • Database and object storage do not share a transaction, so exports have explicit lifecycle states.
  • An identical retry can recover an interrupted export without duplicating the snapshot.
  • Reusing an execution ID for different content returns a conflict instead of overwriting evidence.
  • The API checks the CSV digest at download time and withholds a mismatch.
ASSUMPTIONS & LIMITS

What this design assumes

  • Local Docker demo; no production TLS termination, enterprise IAM or managed key service.
  • Configured bearer credentials represent enrolled identities; no proof the host data is truthful.
  • Database and object storage are trusted together; digests are not immutable against privileged tampering.
  • Retention is configured but automatic deletion is not implemented.
How to explain the security boundary in the interview

What the digest proves: the downloaded CSV matches the digest stored in PostgreSQL at the time of verification. It does not prove that the agent's original observation was true, nor prevent a privileged attacker from changing both the object and database digest.

What authentication proves: the request presented a configured bearer credential associated with a server ID. It does not prove which human initiated the run or that the enrolled host is uncompromised.

What the demo deliberately leaves for production: managed workload identity, human SSO/MFA, key lifecycle, external TLS termination, tamper-resistant audit retention, automated deletion, monitoring and tested recovery.

!

Agent integrity boundary: a script cannot protect itself against a root or administrator controlling its destination host. Signed packages, trusted installation/update controls and, where justified, hardware-backed remote attestation are future design work.
